## Key Points

- **Decision:** Keep vanilla JS + CSS hosted from `expense-api`
- **Rationale:** RadiusClaim is a reference sample for Dapr + Radius portability, not a product UI showcase
- **Cost/benefit:** Framework adds pedagogical friction without advancing the platform story
- **Portability:** Vanilla runs anywhere .NET runs; framework build step introduces Node.js tooling dependency
- **Current state:** UI is polished (semantic HTML, ARIA, CSS custom properties, polling, telemetry, validation) but minimal — intentionally small
- **Reconsider when:** UI becomes the product, multiple routes/complex navigation needed, team composition changes, or separate SPA deployment is desired

## Rationale

The webapp is the demo surface, not the core output. The current vanilla implementation is **not basic** — it's minimal and grown-up. Developers can edit and reload without framework knowledge. The UI story should not distract from Dapr and Radius narrative. Status quo is the correct choice.

## Status

DECISION — approved. Framework migration is not justified at this time. Revisit in Phase 8+ if conditions change.
