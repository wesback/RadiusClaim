# Orchestration Log: Graham Pubsub Triage

## Context

Live deployment failure: `pubsub` recipe fails during `rad deploy`, leaving expense-api-service and expense-api stuck in progress indefinitely. Triggered by Wesley's deployment report.

## Three-Layer Diagnosis

### Layer 1: Design Gap (Low-Impact Observation)

**Finding:**  
`infra/radius/app.bicep` line 115–142: expense-api lacks pubsub connection.

**Connections present:**
- workflow (service invocation)
- state (statestore)
- secrets (platform-secrets)

**Missing:** pubsub connection

**Impact Assessment:**  
This is **likely intentional**. expense-api is the submission boundary, not event publisher. Notification flow (workflow-engine → pubsub → notification-svc) is correctly wired.

**Recommendation:** If expense-api should emit ExpenseSubmitted events, add pubsub to its connections. Current wiring assumes workflow-engine is event origin.

### Layer 2: Recipe Contract Drift (Medium-Impact Root Cause)

**Finding:**  
`infra/radius/recipes/azure/pubsub.bicep` shows output structure misalignment.

**Declaration:**
```bicep
output result object = {
  values: {
    type: 'pubsub.azure.servicebus.topics'
    ...
  }
}
```

**Issue:**  
Recipe outputs `disableEntityManagement: 'true'` (line 73), so Dapr will NOT auto-create subscription. However, pubsub.bicep **does** pre-create `notification-svc` subscription (line 47–54).

**Status:**  
This is **correct wiring**, but metadata contract between recipe output and Dapr component injection may have version skew with Azure Service Bus or Dapr binding version.

**Signal from history:**  
Graham documented "contract drift in pubsub.bicep: queue-style vs. topic-style, missing pre-created notification-svc subscription while disableEntityManagement=true."

### Layer 3: Implicit Deployment Ordering (Critical Root Cause)

**Finding:**  
Dapr components (statestore, pubsub, platform-secrets) are top-level resources in app.bicep (lines 64, 81, 99). Services are modules that **reference** these via `connections` parameters.

**Dependency Mechanics:**  
In Radius, `connections` create **implicit ordering**: container cannot progress past "ready" until connection targets exist.

**Failure Chain:**
1. pubsub recipe deployment fails (Azure Service Bus throttling, missing RBAC, ARM template error)
2. Recipe output (namespace FQDN + connection string) never materializes
3. Services attempting to connect to pubsub remain in-progress
4. workflowEngine explicitly references pubsub.id; reference cannot resolve
5. expense-api-service has implicit dependency on workflow-engine (service-invocation connection)
6. expenseApiGateway has explicit `dependsOn: [expenseApi]`
7. Entire chain blocks

**Why Services Hang:**  
Not resource contention—it's **unresolvable reference deadlock**. Radius orchestrator cannot evaluate downstream module connections until failed upstream resource succeeds.

## Recommended Checks (Priority Order)

1. **Azure Service Bus deployment status:**
   - Verify namespace provisioning succeeded: `az servicebus namespace list`
   - Check Radius deployment logs for ARM template error
   - Signal: "pubsub failed" = recipe's `Microsoft.ServiceBus/namespaces` resource deployment failed

2. **Dapr component injection state:**
   - Check Radius environment: `rad resource list`
   - Expected: statestore, pubsub, platform-secrets all `Ready` or `Provisioning`
   - If pubsub missing/errored: recipe output never produced, downstream blocked

3. **Service deployment trace:**
   - Examine expense-api-service pod logs (AKS/ACA)
   - Look for: "statestore not available", "workflow-engine timeout", Dapr sidecar failure
   - Expected: correct wiring = sidecars inject and log connection details at startup

4. **Recipe contract validation:**
   - If pubsub exists but services hang: validate Dapr component config matches recipe output
   - Confirm `disableEntityManagement: 'true'` set correctly
   - Verify pre-created subscription `notification-svc` exists in Service Bus
   - Inspect Dapr component manifest or connection-string secret in Radius environment

## Recommended Next Steps

1. **Verify Service Bus deployment success** (highest signal)
   - Confirm namespace FQDN and connection string provisioned
   
2. **Check Dapr component visibility** in Radius environment
   - If pubsub component exists but stuck, trace why (likely Azure RBAC or metadata mismatch)

3. **If pubsub ready, validate expense-api logs** for stalled connection handshakes or missing sidecar injection

4. **If all Dapr components ready but services hang**, issue moves from platform wiring to app-level deadlock (service-invocation loop, initialization order)

## Platform-Level Decision

**Keep pubsub recipe as-is** (topics + pre-created subscription with entity management disabled). Design is sound.

**Failure attribution:**
- If pubsub deployment fails → **Azure provisioning issue**, not Radius wiring
- If services hang post-provisioning → **Dapr sidecar injection or app-level initialization**, not recipe structure

**App Team Note:**  
If expense-api should emit events (ExpenseSubmitted), add pubsub to its connections. Current wiring assumes expense-api is submission-only.
