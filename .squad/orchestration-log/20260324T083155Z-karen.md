## Decision: Script-Based Integration Testing

**Verdict:** Approved

Phase 7 validation uses an **executable bash script** (`scripts/validate-deployment.sh`) as the primary integration validation artifact instead of adding a new test framework (e.g., xUnit integration tests, Playwright, etc.).

### Context

Phase 7 requires "the strongest realistic integration-validation artifact without inventing infrastructure." The repo characteristics:

- No existing test projects or test frameworks
- Application code is Dapr-based and requires distributed runtime (sidecar, state store, pub/sub)
- CI/CD workflow already has inline end-to-end validation logic
- Sample targets enterprise/platform audiences who need executable validation, not just documentation

### Options Considered

| Option | Status | Rationale |
|--------|--------|-----------|
| xUnit integration test project | Rejected | Invents infrastructure, adds dependencies |
| Playwright E2E framework | Rejected | Overkill for API-only validation, invents infrastructure |
| Standalone bash script (extracted from CI/CD logic) | **Selected** | Uses existing pattern, executable, no new dependencies |
| Documentation checklist only | Rejected | Doesn't prove distributed behavior; lowers trust bar |

## What the Script Validates

The script proves **distributed system behavior**:
- State persistence (Dapr state store)
- Workflow orchestration (Dapr Workflow)
- Service invocation (expense-api → workflow-engine)
- Approval thresholds ($50 auto-approve, $150 manual-review, $100.00 boundary)
- Status transitions end-to-end

**Not** just "the service started" validation — it exercises the full Dapr-backed flow.

## Usage

**Standalone:**
```bash
./scripts/validate-deployment.sh https://<expense-api-fqdn>
```

**Already integrated in CI/CD** (`.github/workflows/deploy-azure.yml`):
