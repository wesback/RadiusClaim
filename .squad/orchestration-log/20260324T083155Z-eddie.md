## Design Rationale

### Honesty Over Abstraction

The sample has a real gap: **Radius does not support Azure Container Apps.** Rather than pretending it doesn't exist, the documentation:
- Labels both paths clearly
- Explains why each exists
- Documents when the fallback can disappear
- Shows that app code is unaffected (Dapr is the portability layer)

### Configuration Transparency

Teams often fail because they don't understand which secret/variable maps to which path. The README makes it explicit with clear path-specific notes:
- `RADIUS_KUBECONFIG` → Radius-first only
- `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` → ACA fallback only
- `AZURE_SUBSCRIPTION_ID` → Both paths

### Demo as Specification

The walkthrough doesn't just say "auto-approves expenses under $100." It shows:
1. Exact `curl` command to submit
2. Exact JSON response structure
3. Exact status progression
4. Exact log output to expect
5. Where to find logs

This makes the demo **reproducible**.

### Roadmap Credibility

The ADR lists three futures when the fallback can disappear:
1. Radius adds ACA support
2. ACA adds Kubernetes API compatibility
3. Organizational strategy shifts to another platform

Credible because it's tied to external roadmaps and documented constraints.
