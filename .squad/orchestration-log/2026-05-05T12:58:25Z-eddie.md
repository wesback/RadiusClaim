## Summary

Eddie conducted a comprehensive review of `docs/blog/portability.md` focusing on narrative flow, tone consistency, reader engagement, and alignment with Microsoft's positioning around sovereignty and portability.

## Key Findings

1. **Narrative Structure:** The blog currently conflates portable app code with the full platform portability story. Eddie identified that the narrative needs to clearly distinguish between what the app achieves (Dapr-portable across orchestrators) and what the current platform implementation provides (Azure-backed recipes).

2. **Tone & Engagement:** Writing is accessible and compelling, but authority is weakened when claims about automatic Dapr component projection or a fully shipped local Radius path are presented without caveats about the current implementation state.

3. **Microsoft Alignment:** The story of sovereign app code is strong and aligns with Microsoft's broader themes, but the sample walkthrough must ground those themes in the repo's actual shipped behavior, not aspirational future capabilities.

## Decision Output

Eddie co-authored the decision **"Eddie Decision — Portability blog must follow the shipped repo story"** (2026-06-13) which establishes that blog content must describe only the currently supported story:
- Kubernetes-first on AKS with Azure-backed recipes
- Dapr as the portable app boundary
- Azure services (PostgreSQL, Service Bus, Key Vault) as current recipes
- Explicit post-deploy component projection requirement
- Local development via checked-in `infra/dapr/local`, not local Radius

## Impact

This decision constrains future blog and documentation work to maintain narrative coherence between app model, deployment scripts, and external positioning. Blog readers will now encounter consistent claims across all channels.
