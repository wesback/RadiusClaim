# Orchestration: Pete — fix-spn-catchtwentytwo

**Timestamp:** 2026-03-27T09:38:00Z  
**Agent:** Pete (Infrastructure Automation Specialist)  
**Work:** Fixed catch-22 in prepare-cluster.sh — az role assignment and az group create were running as the SPN (via env vars) instead of the user's own account.

## Summary

When Azure service principal credentials (`AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_TENANT_ID`) are set in the environment, the Azure CLI (`az`) uses those credentials for **all** commands, not just the ones that need them. This creates a chicken-and-egg problem when the script needs to:

1. Create a service principal
2. Assign the Contributor role to that service principal
3. But the SPN doesn't have `Microsoft.Authorization/roleAssignments/write` permission yet

The script was failing at step 2 because it was trying to assign the role **as the SPN**, which doesn't have that permission.

## Solution

Temporarily unset the SPN environment variables (`AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_TENANT_ID`) before privileged `az` operations, allowing the Azure CLI to fall back to the user's own authentication (from `az login`). After the privileged operation completes, restore the SPN env vars so subsequent commands that DO need the SPN (like `rad credential register`) continue to work.

### Pattern Applied

```bash
# Save SPN env vars before privileged operation
local saved_client_id="${AZURE_CLIENT_ID:-}"
local saved_client_secret="${AZURE_CLIENT_SECRET:-}"
local saved_tenant_id="${AZURE_TENANT_ID:-}"

# Unset so az uses user's own login
unset AZURE_CLIENT_ID AZURE_CLIENT_SECRET AZURE_TENANT_ID

# Run privileged operation as user
az role assignment create --assignee "$app_id" --role Contributor --scope "/subscriptions/$sub_id"

# Restore SPN env vars
export AZURE_CLIENT_ID="$saved_client_id"
export AZURE_CLIENT_SECRET="$saved_client_secret"
export AZURE_TENANT_ID="$saved_tenant_id"
```

## Rationale

- User's Azure identity (from `az login`) has sufficient permissions to create resources and assign roles
- Service principals typically lack `Microsoft.Authorization/roleAssignments/write`
- Temporarily unsetting env vars lets user credentials take precedence for privileged operations
- Restoring env vars ensures subsequent SPN-scoped operations (like `rad credential register azure sp`) work
