# Orchestration Log: Daisy Pubsub Triage

## Context

Live deployment failure: `pubsub` resource enters FAILED state during `rad deploy`, blocking downstream service modules (expense-api-service, expense-api) in indefinite in-progress loop.

## Diagnosis Delivered

### Observed Symptom
- ✅ platform-secrets — complete
- ✅ statestore — complete
- ✅ radiusclaim (app resource) — complete
- ❌ pubsub — **FAILED**
- 🔄 expense-api-service — **stuck in progress**
- 🔄 expense-api — **stuck in progress**

### Root Cause: Failed Dependency Deadlock

**The dependency chain:**
1. `app.bicep` declares pubsub as a top-level resource
2. workflowEngine and notificationService modules reference `pubsub.id` in their connection declarations
3. When pubsub fails (recipe execution error), it cannot produce `.id` output
4. Downstream modules cannot resolve `pubsub.id` → unresolvable reference
5. Radius orchestrator enters wait loop that never resolves because pubsub is **failed**, not incomplete

**Result:** Services remain in "progress" forever. They cannot be created until pubsub succeeds, but pubsub has already failed.

### Likely Pubsub Failure Causes

1. **Recipe output contract mismatch** — azure-servicebus-pubsub recipe outputs Dapr component type that doesn't match what Radius expects
2. **Parameter passthrough failure** — namespaceName, topicName, subscriptionName parameters malformed or unknown
3. **Recipe template not found or unpublished** — OCI artifact inaccessible or missing in cluster context

### Architectural Pattern Confirmed

- Radius dependency tracking through resource `.id` references is **correct**
- Service-to-Dapr-component wiring is **architecturally sound**
- Failure mode (deadlock on failed dependency) is an **operational lesson**, not a design flaw

## Immediate Actions

1. **Verify pubsub recipe health:**
   - Check if recipe OCI image exists and is accessible
   - Confirm recipe Bicep compiles: `az bicep build --file infra/radius/recipes/azure/pubsub.bicep`
   - Verify recipe output contract matches Dapr pubsub type

2. **If recipe is healthy but fails:**
   - Check Radius provider logs: `rad resource logs pubsub --application radiusclaim`
   - Confirm parameters (namespaceName, topicName, subscriptionName) correctly passed

3. **Isolate the failure:**
   - Deploy just pubsub component in isolation (skip service modules)
   - Prove failure is pubsub-specific vs. downstream effect

4. **Gate Phase 7 re-validation:**
   - Do NOT re-attempt full `rad deploy` until pubsub succeeds in isolation
   - Once pubsub succeeds, service modules should immediately progress

## For Future Reference

- Recipe failures are **NOT idempotent**: `rad deploy` cannot recover by retrying broken recipe
- Pre-deployment recipe validation (compilation + type checking) must be CI gate before `rad deploy`
- Single failed recipe can block entire application deployment—operational lesson captured
